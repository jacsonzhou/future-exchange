## 1. 需求文档审查（产品经理视角）

### 1.1 ✅ 优点

1. **对标分析清晰**：Binance/OKX/Bybit对比完整
2. **功能模块划分合理**：事件消费、订单创建、监控、计算、事件发布
3. **数据模型设计完整**：表结构设计合理，索引优化到位
4. **性能目标明确**：延迟、吞吐量指标清晰

### 1.2 ❌ 关键问题

#### 问题1：订单执行监控机制不明确

**现状**：
- 需求提到"每100ms查询一次订单状态"
- 但未说明：
  - 如何消费Kafka订单状态事件？
  - 如何避免轮询带来的延迟？
  - 如何处理订单状态丢失？

**建议**：
- ✅ 使用Kafka消费`order-state-{symbol}`事件（实时）
- ✅ 保留定时轮询作为兜底机制（每5秒）
- ✅ 实现订单状态机，确保状态流转正确

#### 问题2：盈亏计算逻辑不完整

**现状**：
- 需求提供了基本公式
- 但未说明：
  - 如何获取实际成交价格？
  - 如何处理部分成交？
  - 如何与Ledger对账？

**建议**：
- ✅ 从TradeEvent获取实际成交价格
- ✅ 支持增量计算（部分成交时）
- ✅ 实现对账机制，确保与Ledger一致

#### 问题3：保险基金交互缺失

**现状**：
- 需求提到"与保险基金服务交互"
- 但未说明：
  - 调用接口定义？
  - 幂等性如何保证？
  - 失败如何处理？

**建议**：
- ✅ 定义保险基金服务接口（Feign Client）
- ✅ 使用`liquidationId`作为`bizSeq`保证幂等
- ✅ 失败重试3次，失败后告警人工介入

#### 问题4：金融规范不足

**缺失内容**：
1. **审计日志**：
   - 所有强平操作必须记录审计日志
   - 包含操作人、时间、原因、结果
   - 不可删除、不可修改

2. **对账机制**：
   - 每日对账：强平记录 vs Ledger分录
   - 异常告警：差异超过阈值告警
   - 对账报告：生成对账报告供审计

3. **异常处理规范**：
   - 定义异常分类（系统异常、业务异常）
   - 定义异常处理流程（重试、降级、人工介入）
   - 定义异常告警规则

#### 问题5：极端行情应对不足

**缺失内容**：
1. **降级策略**：
   - OMS不可用时：缓存事件，延迟处理
   - 大量强平时：队列削峰，优先级处理
   - 价格剧烈波动：限价单保护，避免滑点过大

2. **熔断机制**：
   - 失败率 > 5%：熔断，人工介入
   - 延迟 > 500ms：降级，简化流程

#### 问题6：数据一致性保证不足

**缺失内容**：
1. **快照一致性**：
   - 强平时需要读取Position快照
   - 如何保证快照是最新的？
   - 如何处理快照延迟？

2. **最终一致性**：
   - 强平记录与Ledger分录最终一致
   - 如何保证？补偿机制？

### 1.3 ⚠️ 需要补充的需求

#### 补充1：强平预警机制

**需求**：
- 在强平触发前，推送预警通知给用户
- 预警阈值：保证金率 < 150%（可配置）
- 预警方式：WebSocket推送、短信、邮件

**优先级**：P1

#### 补充2：强平价格优化

**需求**：
- 大仓位强平时，使用TWAP（时间加权平均价格）策略
- 避免单笔大单冲击市场
- 分多笔订单，每笔间隔100ms

**优先级**：P1

#### 补充3：强平统计报表

**需求**：
- 实时统计：强平数量、穿仓损失、保险基金使用
- 历史报表：按日/周/月统计
- 告警报表：异常强平、大额穿仓

**优先级**：P2

### 2.3 性能问题

#### 问题1：Kafka消费配置不合理

**现状**：
```yaml
# application.yml
max.poll.records: 500  # ⚠️ 批量太大，可能导致处理延迟
auto-commit-interval-ms: 1000  # ⚠️ 自动提交，可能丢失消息
```

**建议**：
```yaml
max.poll.records: 100  # 减小批量，降低延迟
enable-auto-commit: false  # 手动ACK，保证不丢失
```

#### 问题2：数据库连接池配置

**现状**：
```yaml
max-active: 20  # ⚠️ 可能不够，强平时并发高
```

**建议**：
```yaml
max-active: 50  # 增加连接池大小
```
