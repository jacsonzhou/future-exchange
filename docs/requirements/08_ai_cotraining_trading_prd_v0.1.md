# AI共训交易系统 PRD（MVP）

## 1. 文档信息
- 文档版本: `v0.1`
- 创建日期: `2026-03-02`
- 适用阶段: `MVP + 3个月执行路线`
- 产品定位: `人机共训交易系统（交易执行 + 能力评估 + 策略迭代）`

## 2. 背景与机会
当前市场上常见产品有两类:
1. 交易所: 侧重撮合、深度、交易体验，弱化用户能力成长。
2. 挑战赛/考核类: 侧重是否达标，弱化持续迭代。

本项目机会点:
1. 用户不仅要交易，还要知道自己是否在进步。
2. AI不仅要给方向，还要可解释、可复盘、可迭代。
3. 人与AI必须使用同一能力度量体系，避免只比收益率。

## 3. 产品定义
### 3.1 一句话定义
`让用户和AI在同一市场、同一评分体系下持续提升交易能力的系统。`

### 3.2 核心闭环
1. 市场与账户数据输入。
2. AI或用户做出交易决策。
3. 模拟执行与结果回传。
4. Skill Score能力评估。
5. 复盘与策略迭代。

### 3.3 当前阶段共识（已锁定）
1. MVP = `模拟盘 + Skill Score + 复盘实验室 + AI建议填单`。
2. Claude/Codex仅在决策层，不直接持有密钥执行下单。
3. 平台对赌放到第三阶段，先做增长和闭环。

## 4. 目标与非目标
### 4.1 MVP目标
1. 让用户在1周内完成至少2次“交易->复盘->调整”的闭环。
2. 让AI建议具备可解释性并可被一键采纳填单。
3. 形成统一Skill Score，支持人与AI同榜比较。

### 4.2 MVP非目标
1. 不做真实资金自动化托管。
2. 不做平台对手盘对赌。
3. 不承诺收益率，不提供投资保证。

## 5. 用户与场景
### 5.1 目标用户
1. 新手交易用户: 需要明确训练路径和风险约束。
2. 进阶交易用户: 需要策略迭代、复盘分析和能力画像。
3. AI策略开发者: 需要标准化输入输出、可追踪回测与线上验证。

### 5.2 关键场景
1. 用户查看AI建议，点击“一键填单”，再手动确认下单。
2. 用户交易后进入复盘实验室，查看决策理由与结果归因。
3. 用户在Skill榜观察自身与AI的差距并调整策略参数。

## 6. 价值主张
### 6.1 对用户价值
1. 既能交易，也能训练自己。
2. 每笔决策有解释，不是黑箱信号。
3. 看到能力趋势，而非只看短期盈亏。

### 6.2 对平台价值
1. 从“交易工具”升级为“能力增长平台”。
2. 形成高粘性闭环行为数据（交易、解释、复盘、迭代）。
3. 为后续订阅、竞技场、策略服务建立商业基础。

## 7. 产品范围（MVP）
### 7.1 模块A: 模拟盘交易
功能要求:
1. 接入真实行情（币安）驱动模拟成交。
2. 支持市价/限价、杠杆、开平仓、撤单。
3. 提供账户资产、持仓、挂单、PnL视图。

验收标准:
1. 用户能在交易页完成下单到成交闭环。
2. 所有成交记录可追溯到订单ID与时间戳。

### 7.2 模块B: Skill Score（人机同尺）
功能要求:
1. 输出统一分数 `0-100`。
2. 同时适用于用户和AI策略。
3. 展示分项得分: 收益质量、风控纪律、执行稳定性。

建议公式（v1）:
`Skill Score = 35% 风险调整收益 + 25% 回撤控制 + 20% 执行质量 + 20% 稳定性 - 违规惩罚`

验收标准:
1. 每个账户每日生成至少1条评分快照。
2. 榜单和个人战绩页面分数一致。

### 7.3 模块C: 复盘实验室
功能要求:
1. 支持按订单回放“当时市场快照+决策理由+执行结果”。
2. 展示策略改进建议（例如仓位、止损、频率）。
3. 可保存复盘结论并关联策略版本。

验收标准:
1. 用户可打开任意一笔历史交易并完成复盘记录。
2. 复盘记录可在后续策略版本中被引用。

### 7.4 模块D: AI建议填单
功能要求:
1. AI输出结构化建议: 方向、建议进场、止损、止盈、置信度、理由。
2. 提供“一键填单”，仅填入参数，不直接执行。
3. 用户仍需最终确认下单。

验收标准:
1. 一键填单后，订单面板参数完整且可编辑。
2. AI建议不可绕过风控直接成交。

## 8. 决策层与执行层边界（Claude/Codex）
### 8.1 角色定义
1. 决策层（Claude/Codex）:
   生成交易意图与解释，不直接调用交易密钥。
2. 执行层（Execution Agent）:
   接收结构化意图，通过风控校验后才能发单。
3. 风控层（Policy Engine）:
   对杠杆、仓位、日损、连续亏损等进行硬约束。

### 8.2 硬性约束
1. LLM不持有用户API Key。
2. 所有下单必须经过Policy Engine。
3. 所有决策与执行过程必须可审计。

## 10. 关键流程
### 10.1 AI建议填单流程
1. 前端请求ContextPack。
2. 决策层返回DecisionIntent。
3. 前端展示建议与理由。
4. 用户点击“一键填单”仅写入表单。
5. 用户确认后走既有下单API。
6. 执行结果回流到复盘与评分模块。

### 10.2 复盘流程
1. 用户选择历史订单。
2. 系统加载当时市场快照+决策+执行反馈。
3. 系统输出归因与改进建议。
4. 用户保存复盘结论并关联策略版本。

## 11. 风控与安全
### 11.1 交易风控（MVP）
1. 单笔名义价值上限。
2. 单账户杠杆上限。
3. 日内最大亏损阈值。
4. 连续亏损触发冷却期。

### 11.2 系统安全
1. 决策日志与执行日志不可篡改（至少保留90天）。
2. 决策请求、响应、执行全链路具备traceId。
3. 用户敏感凭据不进入模型上下文。

## 12. 指标体系（上线后追踪）
### 12.1 增长指标
1. 新用户7日留存（目标: `>=25%`）。
2. 周活跃复盘用户占比（目标: `>=35%`）。

### 12.2 产品闭环指标
1. 每周“交易->复盘->调整”闭环次数（目标: 人均`>=2`）。
2. AI建议采纳率（目标: `>=20%`）。
3. 复盘后策略参数修改率（目标: `>=30%`）。

### 12.3 风险指标
1. 风控拦截准确率（误拦截率目标: `<3%`）。
2. 违规越权下单次数（目标: `0`）。

## 13. 3个月路线图
### 月份1（第1-4周）: 模拟闭环上线
1. 完成模拟盘核心交易流程稳定化。
2. 上线Skill Score v1。
3. 上线复盘实验室 v1。
4. 上线AI建议填单 v1（手动确认执行）。

里程碑产出:
1. MVP可对外灰度。
2. 人机同榜可查看基础分数。

### 月份2（第5-8周）: 半自动能力
1. 引入策略版本管理（v1/v2/A-B）。
2. 引入决策模板与场景化策略（趋势、震荡）。
3. 增强归因分析（滑点、执行偏差、风险暴露）。
4. 建立AI协作增益指标（人机协作收益对比）。

里程碑产出:
1. 用户可看到自己策略版本迭代效果。
2. 平台形成稳定复盘数据沉淀。

### 月份3（第9-12周）: 受控自动化准备
1. 白名单模式自动执行（小流量、低风险币对）。
2. 增加熔断与异常停机机制。
3. 完善审计与监管报表准备能力。
4. 设计第三阶段“平台对赌”风险模型，不上线真实对赌。

里程碑产出:
1. 受控自动化试点可运行。
2. 第三阶段商业与合规方案评审通过。

## 14. 平台对赌策略（第三阶段）
### 14.1 当前策略
1. MVP和前两个月不做平台对赌。
2. 优先做模拟盘增长与训练闭环。

### 14.2 第三阶段准入条件
1. 风控模型经历史数据验证。
2. 法务与合规评审完成。
3. 具备充分保险/准备金与风险预算机制。

## 15. 技术实现建议（结合现有系统）
### 15.1 建议复用现有模块
1. `market-price-core`: 行情与K线。
2. `oms-core`: 下单、撤单、状态流转。
3. `public-push-core/private-push-core`: 实时推送。
4. `api-gateway`: 对外统一接口。

### 15.2 新增建议模块
1. `ai-decision-core`（决策服务）:
   输入ContextPack，输出DecisionIntent。
2. `skill-score-core`（评分服务）:
   定时计算分数并写入快照。
3. `replay-lab-core`（复盘服务）:
   聚合决策、执行与行情证据。

### 15.3 调用原则
1. 同步调用使用Feign + `lb://service-name`。
2. 异步事件通过Kafka Topic解耦。
3. 禁止跨服务直接new或类注入。

## 16. 验收标准（MVP）
1. 用户可在一个会话内完成: 查看AI建议 -> 一键填单 -> 确认下单 -> 查看结果。
2. 每笔订单可关联: 决策ID、评分快照、复盘记录。
3. Skill Score可在首页/交易页/榜单一致展示。
4. 全链路日志可追溯并支持问题定位。

## 17. 风险与对策
1. 风险: 用户误解AI建议为收益承诺。
   对策: 明确风险提示，展示置信度和适用场景，不展示收益保证文案。
2. 风险: 模型幻觉导致异常建议。
   对策: 结构化输出 + 风控硬限制 + 用户确认。
3. 风险: 评分被刷分或失真。
   对策: 引入违规惩罚项与异常行为检测。

## 18. 待确认问题
1. Skill Score是否先采用日频刷新，还是分钟级准实时刷新。
2. 复盘建议由规则引擎先实现，还是直接接入模型生成。
3. 白名单自动化试点的用户筛选标准与风险预算。

## 19. 发布建议
1. 先灰度给内部用户和种子用户。
2. 每周固定一次评分模型review。
3. 每两周一次功能迭代发布，保持闭环节奏。
