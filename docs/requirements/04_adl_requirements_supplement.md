# ADL需求文档补充 - 关键缺失项

## 1. ADL执行价格机制补充

### 问题：
需求文档提到"使用穿仓用户的破产价格"，但在实际实现中存在歧义。

### 补充方案：
```
ADL执行价格选择逻辑：
1. 优先使用：当前标记价格（Mark Price）
2. 备选方案：破产价格（Bankruptcy Price）
3. 选择规则：
   - 正常情况：使用标记价格（更公平）
   - 极端情况：标记价格偏离过大时，使用破产价格
   - 价格偏离阈值：|markPrice - bankruptPrice| / bankruptPrice > 5%
```

**原因**：标记价格更公平，避免被ADL用户因价格不利而产生额外损失。

## 2. ADL执行批次控制

### 问题：
需求文档未明确大额穿仓时的分批ADL策略。

### 补充方案：
```
批次控制规则：
1. 单批次最大用户数：50人
2. 单批次最大金额：100万USDT
3. 批次间隔时间：500ms
4. 最大批次数：10批
5. 超出10批后：触发系统熔断，人工介入

批次执行流程：
- 第1批：选择排名1-50的用户
- 第2批：选择排名51-100的用户
- ...
- 每批执行后重新计算剩余损失
```

## 3. ADL幂等性保证机制

### 问题：
需求文档提到bizSeq字段但未说明幂等性实现。

### 补充方案：
```
幂等性保证：
1. 唯一键：bizSeq = ADL_{liquidationId}_{targetUserId}_{executionSequence}
2. 数据库层：UNIQUE KEY on bizSeq
3. 应用层：执行前检查是否已存在该bizSeq的记录
4. 分布式锁：基于Redis的分布式锁，锁key = "adl_lock_{liquidationId}"
5. 锁超时时间：30秒

执行流程：
1. 尝试获取分布式锁
2. 检查bizSeq是否存在
3. 执行ADL
4. 记录执行结果
5. 释放锁
```

## 4. ADL二次校验机制

### 问题：
从选择候选人到执行ADL之间存在时间间隔，候选人持仓可能已变化。

### 补充方案：
```
二次校验规则：
1. 执行前校验：
   - 候选人持仓是否还存在
   - 候选人持仓数量是否足够
   - 候选人是否还在盈利状态
   - 候选人账户是否正常（未冻结）

2. 校验失败处理：
   - 跳过该候选人
   - 自动选择下一个候选人
   - 记录跳过原因到日志

3. 重试机制：
   - 最多重试3次
   - 每次重试重新拉取候选人列表
   - 3次失败后触发人工告警
```

## 5. ADL预警通知机制

### 问题：
需求文档只有ADL执行后通知，缺少预警机制。

### 补充方案：
```
ADL预警通知：
1. 危险区划分：
   - 绿色区：排名 > 50% （安全）
   - 黄色区：20% < 排名 <= 50% （注意）
   - 橙色区：10% < 排名 <= 20% （警告）
   - 红色区：排名 <= 10% （危险）

2. 通知策略：
   - 进入黄色区：站内信通知
   - 进入橙色区：站内信 + Push通知
   - 进入红色区：站内信 + Push + 邮件 + 短信
   - 执行ADL：全渠道通知

3. 通知频率限制：
   - 同一用户同一档位：1小时内最多通知1次
   - ADL执行：实时通知，不限频
```

## 7. 保险基金不足时的降级策略

### 问题：
需求文档未说明保险基金完全耗尽后的处理。

### 补充方案：
```
降级策略：
1. 保险基金充足（> 50%阈值）：
   - 正常赔付穿仓损失
   - 不触发ADL

2. 保险基金不足（10% ~ 50%阈值）：
   - 部分赔付 + ADL分摊
   - 赔付比例 = 当前余额 / 穿仓损失

3. 保险基金危险（< 10%阈值）：
   - 保留最低余额不使用
   - 全部穿仓损失由ADL分摊
   - 触发平台告警

4. 保险基金耗尽（= 0）：
   - 系统熔断
   - 禁止新开仓
   - 人工介入补充保险基金
```

## 8. ADL限流与熔断机制

### 问题：
需求文档未考虑极端市场下的ADL风暴。

### 补充方案：
```
限流机制：
1. 频率限制：
   - 单symbol：每10秒最多触发1次ADL
   - 全局：每10秒最多触发5次ADL

2. 数量限制：
   - 单次ADL：最多影响50个用户
   - 5分钟内：最多影响200个用户

熔断机制：
1. 触发条件：
   - 5分钟内ADL次数 > 10次
   - 5分钟内ADL影响用户 > 200人
   - 保险基金下降速度 > 50%/5分钟

2. 熔断动作：
   - 暂停所有新开仓
   - 提高维持保证金率（临时提升20%）
   - 强制降低杠杆（最高10x）
   - 发送紧急告警

3. 熔断恢复：
   - 市场稳定后（波动率下降）
   - 保险基金补充到安全水位
   - 人工确认后手动恢复
```

## 9. ADL历史数据归档策略

### 问题：
ADL执行记录会快速增长，需要归档策略。

### 补充方案：
```
归档策略：
1. 热数据（保留在主表）：
   - 最近30天的ADL记录
   - 支持实时查询

2. 温数据（归档到历史表）：
   - 30天～1年的ADL记录
   - 查询延迟可接受

3. 冷数据（归档到对象存储）：
   - 1年以上的ADL记录
   - 按需加载

4. 归档任务：
   - 执行频率：每天凌晨2点
   - 归档粒度：按天归档
   - 保留策略：冷数据保留7年（监管要求）
```

## 10. ADL测试用例补充

### 新增测试场景：

#### 场景1：并发ADL
```
条件：
- 同时有2个用户穿仓
- 需要ADL同一批候选人

期望：
- 第1个ADL正常执行
- 第2个ADL能正确处理候选人持仓已减少的情况
- 不会出现超量ADL
```

#### 场景2：候选人不足
```
条件：
- 穿仓损失 = 10万USDT
- 对手方盈利仓位总额 = 5万USDT

期望：
- ADL所有对手方盈利仓位
- 剩余5万USDT损失由保险基金承担
- 触发保险基金不足告警
```

#### 场景3：ADL执行中候选人被其他操作平仓
```
条件：
- ADL选中用户A
- 执行ADL前，用户A自行平仓

期望：
- ADL二次校验失败
- 自动跳过用户A
- 选择下一个候选人
```

## 11. 监控指标补充

### ADL核心监控指标：
```
1. 业务指标：
   - ADL触发次数（按symbol、按时间段）
   - ADL影响用户数
   - ADL平均执行时长
   - ADL成功率
   - 保险基金余额
   - 保险基金使用率

2. 技术指标：
   - ADL排名计算延迟
   - ADL执行延迟（P50/P95/P99）
   - Kafka消费延迟
   - 数据库连接池使用率

3. 告警规则：
   - ADL执行失败：立即告警
   - ADL执行时长 > 5秒：告警
   - 保险基金 < 警告阈值：告警
   - 保险基金 < 危险阈值：紧急告警
   - ADL排名计算延迟 > 3秒：告警
```

## 12. 下单平仓流程整合

### ADL与下单流程的关系：

```
正常平仓流程：
用户发起 → Order Service → Risk Check → Match Engine → Clearing

ADL强制平仓流程：
ADL触发 → 生成ADL订单 → 绕过Risk Check → Match Engine → Clearing
                                ↑
                            特殊标记：
                            - orderType = ADL
                            - price = markPrice
                            - timeInForce = IOC
                            - bypass风控
```

### ADL订单特殊处理：
1. **风控豁免**：ADL订单绕过保证金检查
2. **撮合优先**：ADL订单优先级高于普通订单
3. **价格固定**：ADL订单使用固定价格（标记价格）
4. **立即成交**：ADL订单必须立即完全成交，否则失败
