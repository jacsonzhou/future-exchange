# 止盈止损订单需求补充 (Supplement)

## 1. 仓位变化处理

### 1.1 加仓场景
```
用户持仓: 1 BTC (多单)
TP/SL订单: 止盈 1 BTC @ 55000
用户操作: 加仓 0.5 BTC

处理方案A (推荐): TP/SL数量不自动调整，用户需手动设置
处理方案B: 按比例自动调整TP/SL数量为 1.5 BTC
```

**建议**: 采用方案A，避免自动调整带来的用户困惑

### 1.2 减仓场景
```
用户持仓: 1 BTC (多单)
TP/SL订单: 止盈 1 BTC @ 55000
用户操作: 减仓 0.3 BTC，剩余 0.7 BTC

处理方案:
- 如果 TP/SL数量 > 持仓数量，自动调整为持仓数量
- 发送通知告知用户TP/SL数量已调整
```

### 1.3 完全平仓
```
持仓完全平仓后:
1. 自动撤销所有关联的 TP/SL 订单
2. 记录撤销原因: "Position closed"
3. 发送通知
```

## 2. 多个TP/SL订单的优先级与执行策略

### 2.1 多个止盈订单
```
持仓: 1 BTC @ 50000 (多单)
TP订单1: 0.5 BTC @ 52000 (部分止盈)
TP订单2: 0.5 BTC @ 55000 (部分止盈)

策略:
- 按价格优先: 先触发 52000 的订单
- 触发后其他订单继续有效（如果持仓仍然存在）
- 如果持仓不足，自动调整或撤销数量不足的订单
```

### 2.2 多个止损订单
```
持仓: 1 BTC @ 50000 (多单)
SL订单1: 0.5 BTC @ 48000
SL订单2: 0.5 BTC @ 45000

策略:
- 按价格优先: 先触发 48000 的订单
- 风控优先: 止损订单优先于止盈订单
```

### 2.3 TP和SL同时触发
```
场景: 市场剧烈波动，TP和SL触发条件同时满足

策略:
- **风控优先**: 优先执行 SL 订单
- 取消 TP 订单
- 记录冲突日志
```

## 3. TP/SL与强平的冲突处理

### 3.1 优先级规则
```
强平触发 > SL触发 > TP触发

原因:
- 强平是系统风控的最后防线，必须优先
- SL是用户的风控措施，其次优先
- TP是盈利锁定，最后优先
```

### 3.2 处理流程
```
1. 检测到强平触发:
   - 立即撤销该持仓所有 TP/SL 订单
   - 执行强平流程
   - 记录撤销原因: "Liquidated"

2. 检测到 SL 触发:
   - 检查是否接近强平价
   - 如果保证金率 < 强平阈值，转为强平流程
   - 否则执行 SL 平仓

3. 检测到 TP 触发:
   - 正常执行平仓
```

## 4. 平仓订单失败重试机制

### 4.1 失败场景
```
1. OMS拒绝订单 (风控拒绝)
2. 撮合引擎异常
3. 网络超时
4. 持仓不存在/数量不足
```

### 4.2 重试策略
```java
重试次数: 3次
重试间隔: 100ms / 200ms / 500ms (指数退避)

策略:
- 第1次失败: 100ms后重试，仍用原执行类型(LIMIT/MARKET)
- 第2次失败: 200ms后重试，降级为 MARKET 订单
- 第3次失败: 500ms后重试，MARKET + 紧急标记
- 全部失败:
  - 发送告警
  - 记录失败日志
  - TP/SL订单状态设为 FAILED
```

### 4.3 特殊处理
```
持仓不存在/数量不足:
- 不重试，直接标记为 CANCELLED
- 原因: "Position not found"

风控拒绝:
- 重试1次，如果仍失败则放弃
- 记录风控拒绝原因
```

## 5. TP/SL的费率处理

### 5.1 费率规则
```
执行类型: MARKET
- 使用 Taker 费率
- 因为市价单会立即成交，消耗流动性

执行类型: LIMIT
- 触发后创建限价单
- 如果限价单Maker成交，使用 Maker 费率
- 如果限价单Taker成交，使用 Taker 费率
```

### 5.2 费率计算
```
触发时预估费用:
- 按 Taker 费率计算
- 检查账户余额是否足够支付手续费
- 不足则触发失败，发送通知

实际成交时:
- 按实际成交方式计算费率
- 如果是 Maker 成交，退还差额
```

## 6. 市价平仓的滑点保护

### 6.1 滑点限制
```
默认最大滑点: 0.5% (可配置)

检查逻辑:
1. 触发时记录 triggerPrice
2. 创建市价单时设置 priceLimitRate = 0.5%
3. 如果实际成交价偏离触发价 > 0.5%，拒绝成交
```

### 6.2 滑点过大的处理
```
场景: 市价单滑点超过限制

处理:
1. 取消当前市价单
2. 改用限价单，价格 = triggerPrice ± 0.3%
3. 订单有效期: 10秒
4. 10秒后未成交，重新评估价格或取消
```

### 6.3 配置项
```yaml
tp-sl:
  slippage:
    max-rate: 0.005          # 最大滑点 0.5%
    limit-order-offset: 0.003 # 限价单偏离 0.3%
    limit-order-ttl: 10000    # 限价单有效期 10秒
```

## 7. 部分成交处理

### 7.1 场景分析
```
TP/SL订单: 平仓 1 BTC @ 55000 (市价)
实际成交: 0.7 BTC @ 55010
未成交: 0.3 BTC

原因:
- 流动性不足
- 订单簿深度不够
```

### 7.2 处理策略 (方案A - 推荐)
```
1. 部分成交后，TP/SL订单状态更新为 PARTIAL_FILLED
2. 剩余 0.3 BTC 继续保持市价单挂单
3. 完全成交后，状态更新为 EXECUTED
4. 超时未完全成交 (如 60秒):
   - 取消剩余订单
   - 创建新的 TP/SL 订单，数量 = 剩余未平仓数量
```

### 7.3 处理策略 (方案B - 激进)
```
1. 部分成交后，立即取消剩余订单
2. 剩余 0.3 BTC 自动创建新的 TP/SL 订单
3. 新订单的触发价 = 原触发价
4. 状态: PARTIAL_FILLED_AND_RECREATED
```

**建议**: 采用方案A，避免多次小额成交的手续费损失

### 7.4 状态机扩展
```
ACTIVE → TRIGGERED → PARTIAL_FILLED → EXECUTED
                               ↓
                          TIMEOUT_CANCELLED
                               ↓
                        (创建新TP/SL订单)
```

## 8. 插针保护的增强

### 8.1 多源价格校验
```
触发条件增强:
1. 标记价格触发 (主要)
2. 同时检查指数价格
3. 如果 |标记价格 - 指数价格| > 3%，暂停触发
4. 等待价格收敛后再触发

防止场景:
- 某一交易所异常数据影响标记价格
- 防止因异常数据导致误触发
```

### 8.2 触发延迟机制
```
连续触发确认:
- 价格连续 2 次快照满足触发条件，才真正触发
- 快照间隔: 100ms
- 防止极短时间的价格毛刺

配置:
tp-sl:
  trigger:
    confirmation-count: 2    # 确认次数
    confirmation-interval: 100 # 确认间隔(ms)
```

## 10. 风控前置检查清单

### 10.1 创建TP/SL时的检查
```
1. 持仓存在性检查
   - 必须有对应方向的持仓
   - 持仓状态必须为 ACTIVE

2. 数量检查
   - TP/SL数量 <= 持仓数量
   - 数量必须 > 最小交易数量

3. 价格合理性检查
   - TP止盈价必须在盈利方向
     * 多单: TP触发价 > 持仓均价
     * 空单: TP触发价 < 持仓均价
   - SL止损价必须在亏损方向
     * 多单: SL触发价 < 持仓均价
     * 空单: SL触发价 > 持仓均价

4. 触发价格不能过于极端
   - 不能设置 = 0 或 = MAX_VALUE
   - 与当前价格偏离不能超过 50%

5. 移动止损参数检查
   - 回调比例必须在 [0.1%, 10%] 之间
   - 回调金额必须 > 最小变动价位
```

### 10.2 触发时的检查
```
1. 持仓仍然存在
2. 持仓数量 >= TP/SL数量
3. 账户状态正常 (未被限制交易)
4. 保证金充足 (能够支付平仓手续费)
```

## 11. 性能优化

### 11.1 触发检查优化
```
问题: 100万订单，每次价格更新都要全量扫描

优化方案:
1. 使用 Redis Sorted Set 存储活跃订单
   - Key: tp_sl:active:{symbol}
   - Score: triggerPrice
   - Value: orderId

2. 价格更新时，使用 ZRANGEBYSCORE 快速筛选
   - 多单止盈: ZRANGEBYSCORE 0 markPrice (价格 <= 标记价)
   - 空单止损: ZRANGEBYSCORE markPrice +inf (价格 >= 标记价)

3. 只查询满足触发条件的订单详情
```

### 11.2 数据库优化
```sql
-- 添加复合索引
CREATE INDEX idx_symbol_status_trigger ON t_tp_sl_order(symbol, status, trigger_price);

-- 添加触发方向索引
CREATE INDEX idx_symbol_status_side_trigger ON t_tp_sl_order(
  symbol, status, trigger_side, trigger_price
);
```

## 12. 监控指标

### 12.1 核心指标
```
1. 触发延迟
   - 标记价格更新 → TP/SL触发的时间
   - 目标: P99 < 50ms

2. 执行延迟
   - TP/SL触发 → 平仓订单创建的时间
   - 目标: P99 < 100ms

3. 成功率
   - 触发后成功平仓的比例
   - 目标: > 99.5%

4. 活跃订单数
   - 实时监控各symbol的活跃TP/SL数量
   - 用于容量规划
```

### 12.2 告警规则
```
1. 触发延迟 > 200ms 持续 1分钟
2. 执行失败率 > 1% 持续 5分钟
3. 重试失败次数 > 100 / 分钟
4. 活跃订单数 > 100万
```
