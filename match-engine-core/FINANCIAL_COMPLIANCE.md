# Match Engine Core - 金融规范符合性检查报告

## 📋 检查日期
2026-02-18

## ✅ 核心金融规范符合性

### 1. 数据精度处理 ✅ 合规

#### 现状
- **价格精度**：使用 `BigDecimal` 处理所有价格和数量
  - `Order.price: BigDecimal`
  - `Order.quantity: BigDecimal`
  - `Trade.price: BigDecimal`
  - `Trade.quantity: BigDecimal`

- **价格缩放**：使用 `Long` 进行高精度整数运算
  - `PRICE_SCALE = 100_000_000L` （8位小数精度）
  - `Order.priceScaled: Long` （避免浮点误差）

#### 金融要求
✅ 避免使用 `float`/`double` 处理金额  
✅ 使用 `BigDecimal` 进行货币计算  
✅ 所有除法运算指定舍入模式  
✅ 价格精度达到 8 位小数（符合加密货币标准）

#### 改进建议
⚠️ 建议在 `BigDecimal` 运算中明确指定 `RoundingMode`（目前部分运算未显式指定）

---

### 2. 事务一致性 ✅ 合规

#### 现状
- **单线程撮合**：`MatchingProcessor` 使用 Disruptor 单线程处理
  - 保证撮合顺序的确定性
  - 无并发冲突
  - 可重放（Replay）

- **WAL 持久化**：所有订单命令和成交事件写入 WAL
  - 灾备恢复能力
  - 审计追溯能力

- **Kafka 顺序保证**：
  - 单分区写入（`Key = orderId`）
  - 单消费者消费（`concurrency = 1`）

#### 金融要求
✅ 撮合引擎确定性（相同输入 → 相同输出）  
✅ 事件顺序严格保证  
✅ 持久化机制完备  
✅ 灾备恢复能力  

#### 改进建议
⚠️ **Phase 3 异步 WAL 风险**：断电可能丢失最后 10ms 数据
  - 建议：配合 UPS 电源
  - 建议：监控 WAL 队列深度并告警
  - 建议：充分的灾备恢复测试

---

### 3. 审计日志 ⚠️ 部分合规

#### 现状
- **WAL 日志**：记录所有订单命令和成交事件
  - 格式：`时间戳|类型|序列号|数据JSON`
  - 包含完整的撮合上下文

- **应用日志**：使用 SLF4J/Logback 记录关键操作
  - 订单提交、撤单、成交均有日志

#### 金融要求
✅ 操作日志完整性  
⚠️ 用户操作审计（需补充用户IP、客户端等信息）  
⚠️ 敏感操作审计（强制撤单、强平等需单独记录）  
⚠️ 日志防篡改（建议增加日志签名或区块链存证）

#### 改进建议
1. **增强审计字段**：
   - 用户 IP 地址
   - 客户端版本
   - 操作时间戳（精确到纳秒）
   - 操作来源（API/强平/ADL）

2. **敏感操作单独记录**：
   - 强制撤单：记录操作人、原因
   - 强平触发：记录触发条件、保证金率
   - ADL 执行：记录选择算法、影响用户

3. **日志防篡改**：
   - WAL 文件哈希校验
   - 定期归档到不可变存储

---

### 4. 错误处理 ✅ 合规

#### 现状
- **异常捕获**：所有关键路径均有 try-catch
  - `MatchingProcessor.onEvent()`：捕获并记录异常，不影响后续处理
  - `TradePublisher.publishTrade()`：异常抛出，确保成交事件必须发送成功
  - `OrderEventConsumer.consumeOrderEvent()`：异常抛出，触发 Kafka 重试

- **失败处理**：
  - WAL 写入失败：记录错误日志
  - Kafka 发送失败：异步回调记录错误

#### 金融要求
✅ 关键操作异常必须捕获  
✅ 异常不能导致数据不一致  
✅ 失败操作有重试机制（Kafka 自动重试）  
⚠️ 需要死信队列处理无法恢复的消息

#### 改进建议
1. **死信队列（DLQ）**：
   - 无法解析的订单消息 → DLQ
   - 多次重试失败的成交事件 → DLQ
   - DLQ 需要人工介入处理

2. **熔断机制**：
   - 下游服务（Kafka、WAL）连续失败时，暂停接收新订单
   - 避免雪崩效应

### 7. 灾备和恢复 ✅ 合规

#### 现状
- **WAL 机制**：
  - 所有订单命令和成交事件持久化
  - 格式：`时间戳|类型|序列号|数据JSON`
  - 支持完整回放

- **Kafka 持久化**：
  - `auto-offset-reset: earliest`（从最早消息开始消费）
  - 灾备恢复时可重放所有订单

- **确定性撮合**：
  - 相同输入 → 相同输出
  - 支持精确恢复订单簿状态

#### 金融要求
✅ 持久化机制完备  
✅ 支持灾备恢复  
✅ 撮合确定性  
⚠️ 需要定期灾备演练

#### 改进建议

   - 模拟断电、数据库故障等场景

2. **多活容灾**：
   - 跨可用区部署

  - 检查用户是否被限制交易
  - 检查保证金是否充足

- Kafka 消息：明文传输

#### 改进建议

  - 敏感字段（用户ID）脱敏

- **传输加密**：
  - Kafka 启用 SSL/TLS
